- **19 November 2026, a project's own rules and what holds them.** Done when the project holds `checks/holders.json`, its list of what holds each of its own rules, which `node core/scripts/holders.mjs --own --write` writes with every rule named as held by `"none"` (#662). From this sync on the project's own rules are read as the core's are: those of the rule files its sessions read, as its own files name them (floor rule 3's and those its `SECURITY.md` adds, and the files its `AGENTS.md` and `CLAUDE.md` pull in by an `@` line, none of the core's copy), each a paragraph or item that opens with a bold lead. The list names for each the check, test, simulation or script that fails where it is broken (`"check: tests/style.test.js"`), `"audit"`, `"describes"` for a line that binds no one, or `"none"`; a session that writes a rule may name its holder there in the same pull request. The monthly state report lists the rules with no holder, those read at a session's start first, and the session that takes it files each as a task at the project's pace: a check where one can read the breach exactly, the rule moved to where it is read on need, or a proposal that it goes, which is the owner's to decide. Where a rule file is a copy made from elsewhere, a design document's, the list is made all the same, and a change to the rule goes to whoever writes that source. Nothing fails: neither a rule with no holder nor a wrong line of the list, which the report names with its mend, and no session removes or rewords a rule of the project's on its own reading. The staged cases and the pruning stay the core's, for their cost; a project may write a staged case of its own, and nothing asks it. The cost: one run of the script and a small pull request of a builder's; then each rule with no holder a task at the project's pace.
