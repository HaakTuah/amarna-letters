- **16 November 2026, how code is put together.** Done when the project has taken the shape check (`core/tasks/code-shape.md`): its config stands at `checks/shape.json` (or where its manifest's row *shape check* names it), as the starter kit writes it (`core/setup/template/shape.json.tmpl`), with its "code" the project's own code as git pathspecs and its "tests" its test files; its first baseline stands beside it, written by `node core/scripts/shape.mjs checks/shape.json --first` and committed, and names every reader of the check's under "reads" (one written before the check read C#, Python, JSX, scripts that share one global space, the tests that reach a real clock, those that start another process and the comments that mark a change is written again by `node core/scripts/shape.mjs checks/shape.json --write`, in a pull request of its own; until then what the pull request's base held there is reported, never failed); and `SECURITY.md` names both under rule 3, among the checks on the work, as the starter kit's does. The baseline names the project's files by path: where a scan of the project's own that counts a path named in its tracked text as a use of that code (an unused-code or reference check) fails on it, the scan is made to leave it out, as a file the shape check writes, never an entry of the scan's own list taken out for it, as `--first`, a `--write` that adds an entry and the writer of this step and of each later step whose baseline names a new reader say (#1289). A config's change: the trusted builder's (floor rule 3). From this sync on the copies workflow runs the check on every pull request, in its one job: until the config is there it holds the project to the starter kit's config, with the pull request's base as its baseline, so nothing that stood before fails, and a pull request that adds a function past a mark or an import on a new cycle fails, saying its mend. Once the config and its baseline stand, what stood before is listed there, and the same holds of everything the config names. Three things follow by themselves, none holding up another. The scheduled look keeps an issue for the cleaning the codebase's state makes due and one for each audit by a reader (`core/tasks/cleaning.md`; `core/scripts/dose.mjs`). The project names its systems in the config, each with its paths, the systems it uses, its entrance and its domain, as a task of its own (`core/tasks/code-shape.md`, "Each project names its systems"), listing what then crosses with `SHAPE_BASE=origin/main node core/scripts/shape.mjs --write`. And where its suites are to be held to a time mark, it names each under "suites" and starts it through `node core/scripts/shape.mjs <config> --suite <name> -- <command>`. The check reads JavaScript and TypeScript, JSX among them, C# and Python; a project in another language has nothing more to do for that code, which its audit's reader holds to the same rules. A project whose tests reach a real clock or start another process through a name of its own (a sleep of its test library, a helper that starts a program) adds the name to the config under "clocks" or "processes" (`core/tasks/tests.md`, "A test reaches a real clock or another process only where it guards it"; #457). Where the manifest's "Modules:" is a list, it takes `code-shape.md` and `cleaning.md`, or leaves each out with its reason.
