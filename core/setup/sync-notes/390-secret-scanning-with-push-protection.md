- **16 November 2026, secret scanning with push protection.** Done when GitHub answers, for the project's repository, `"enabled"` for both `security_and_analysis.secret_scanning.status` and `security_and_analysis.secret_scanning_push_protection.status` (`gh api repos/<owner>/<repo>`; `core/floor/topics/weaknesses.md`, topic 9). In a public repository (`"private": false` in the same answer), where GitHub gives it free, a session whose sign-in may change the repository's settings switches both on, `gh api -X PATCH repos/<owner>/<repo> -F 'security_and_analysis[secret_scanning][status]=enabled' -F 'security_and_analysis[secret_scanning_push_protection][status]=enabled'`. In a private repository, where it may be billed per committer, and where the session's sign-in may not, the session files an issue for the owner instead, labelled `needs-owner`, naming the setting (Settings, Advanced Security), and the rest goes on: switching it on there is the owner's (floor rule 14). A repository GitHub gives no secret scanning (its answer holds no `secret_scanning` under `security_and_analysis`) has nothing to do. A private repository whose owner does not want it declares so in its manifest's "Differences", on the owner's word.
