- **20 November 2026, a project read against the core.** Done when the project holds `checks/core-reading.json`, the record of its readings against the core, which marks every rule of its copy as it stood at the last (#464). The first time, the whole project is read: the session that takes the task starts a fresh auditor (`core/roles/auditor.md`), which built none of what it reads and changes nothing, and gives it every rule the project takes, as `node core/scripts/core-reading.mjs --rules` lists them; for each it answers met, partly, not met or not applicable, with its evidence (a file, a count, a pull request) and what holds it in the project: a check, a test, the review, or nothing. The session writes the answers as a report in the project's *audits*, named by its day, files each gap as a task the project's agents take at the dose (`core/tasks/cleaning.md`), a step only the owner can take labelled `needs-owner`, and records the reading with `node core/scripts/core-reading.mjs --recorded`, in one pull request; a weakness goes the way floor rule 9 gives, never into the report. After that, a sync that brings rules added or changed has them read alone, as `node core/scripts/core-reading.mjs` names them; one that jumps from a copy older than the core's last two releases says so, and the record is taken out in a pull request of its own, so that the next reading is whole. Nothing fails or waits on the owner, and nothing of the project's code or findings leaves it: the core gets counts alone, where the manifest shares them. The cost: one long session of an auditor's, once, on the tool's strongest model; then, at each release, a reading of what it changed.
