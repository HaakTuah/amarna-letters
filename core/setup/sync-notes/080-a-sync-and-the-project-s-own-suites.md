- **12 November 2026, a sync and the project's own suites.** Done when a sync PR runs the project's own suites only for what they take from the copy: where its workflows decide which suites a change runs, they count `core/.node-version` for all of them where they run on that Node, a change under `core/scripts/` for the tests that read those scripts, and neither the rest of `core/` nor a workflow in which only the pin of a call to a core workflow moved (`core/README.md`, "How a project takes the core", point 5). A path filter sees which files changed, never what changed in them: a workflow that filters its pull requests by `paths-ignore` lists there, beside `core/**` and `core-manifest.md`, each file that holds only calls to the core's workflows by its exact path (`.github/workflows/core.yml` and the like), and one that filters by `paths` takes each out with `!<its path>`; `core.yml` checks those pins on every pull request. A workflow that stands in for a suite, its `paths` holding each path of the suite's `paths-ignore` and each of its jobs reporting a check the suite reports, by a plain `name` or key (no expression, no matrix), so that a check a ruleset asks for reports where the suite is skipped, is no suite: it gains the same paths under its `paths`, never `!<its path>`, and the step leaves it out; one that shares a check with a suite and is not yet one is named with that mend alone. The checks of the copy, the rule files and the licences run on every sync as before. A project whose suites do not run on its pull requests does nothing. From #1093 a workflow that selects its suites through `core/scripts/select.mjs` has nothing to do: the selection counts the copy's `.node-version` for every test, any other file of the copy for the tests that can run it, and a workflow in which only those pins moved for none.
