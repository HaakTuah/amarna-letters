# What a sync asks of a project

Most changes to the core reach a project by the copy alone. An entry stands here when a project must change something
of its own for a change to hold: a row of its manifest, a line of a rule file, a workflow, an audit.
`core/scripts/sync.mjs` prints the entries a sync brings, and an orchestrator gives them a lane when this file gains
any (`core/modules/orchestrating.md`). Each is done in a PR of its own once the sync PR is merged (a pure sync holds the
copy alone: floor rule 8), or queued in the *progress file* where it is large; none waits for the owner beyond what
the floor names. One that changes a protected file (floor rule 3: a rule file, the manifest, a workflow, a check's
config or audit) is the trusted builder's, never a task given to another provider's. Each entry says how to tell it is done, so a project unsure
where it stands checks them all, and one already done asks nothing. Newest last, each on one line.

- **12 November 2026, builders named by role.** Done when `AGENTS.md` tells a builder of another provider to read `core/modules/other-builders.md` at the start of every task and gives `core/modules/codex.md` to no builder; the manifest's row for what such a builder runs before it finishes is named *other builders' checks* (a row *Codex's checks* is renamed); and the *size marks* and any other config name those files so.
- **12 November 2026, who reviews.** Done when the manifest fills *code reviewers* and *security reviewer* wherever the project's differ from the core's own (`core/README.md`, "Slots"; left out, the core's hold), and the project's own review guidelines call a finding blocking or not, never by one reviewer's priorities.
- **12 November 2026, the core has moved.** Done when a project whose orchestrator does not wake every day has a `core-moved.yml` of its own (`core/README.md`, "How a project takes the core", point 5).
- **12 November 2026, fetches on Windows and by .NET.** Done when the licence check passes: where it fails naming a workflow, a script or a JSON file that runs `dotnet tool install`, `choco`, `winget`, `nuget`, a PowerShell download or the like, that file is named in the "files" of the audit entry of what it fetches. A project whose packages are not npm's also files with the core, once, as an idea (`core/README.md`, "Reporting to the core"), which tool holds its packages to floor rule 10 and how it is run: the tool and its command, nothing of the project.
- **12 November 2026, the default branch.** Done when the `core` check passes: the default branch is `main`.
- **12 November 2026, differences.** Done when no rule of the project's own replaces a module's unlisted: each such rule is dropped where the core's serves, or put to the owner as a line for the manifest's "Differences" (`core/README.md`, "How a project takes the core", point 7), which waits for the owner's word while the module's holds.
- **12 November 2026, a slimmer copy.** Done when the manifest's "Paths:" line reads as `core/README.md`, "The manifest's format", gives it: the core's `reports/` is no longer under `core/`, since the copy leaves that folder in the core.
- **12 November 2026, a sync and the project's own suites.** Done when a sync PR runs the project's own suites only for what they take from the copy: where its workflows decide which suites a change runs, they count `core/.node-version` for all of them where they run on that Node, a change under `core/scripts/` for the tests that read those scripts, and neither the rest of `core/` nor a workflow in which only the pin of a call to a core workflow moved (`core/README.md`, "How a project takes the core", point 5). The checks of the copy, the rule files and the licences run on every sync as before. A project whose suites do not run on its pull requests does nothing.
- **12 November 2026, the way work is handed over.** Done when the project's own rules no longer say how a Claude session hands a task to another provider, or how Codex's or Copilot's review is asked: the core's parts do (`core/modules/roles.md`, "The builders"; `core/modules/orchestrating.md`; `core/modules/codex.md`; `core/modules/copilot.md`), and what truly differs here is a line under the manifest's "Differences". For a tool the core has no part for, the project's rules say in a line each how it is handed a task and asked for a review, and the project files that with the core, once, as an idea (`core/README.md`, "Reporting to the core"): the tool and its commands, nothing of the project. The manifest fills *other builders' checks*, and its *code reviewers* only where its order differs from the core's (Codex, then Copilot where the repository has it, last the fallback reviewer). The rule bars no tool from work the owner gives it in person.
- **12 November 2026, a feature may wait for a later stage.** Done when the manifest's "Differences" no longer lists that a feature whose users do not yet come out ahead may wait for a later stage: `core/modules/game-design.md`, "Using a feature must pay, measured three ways", says so now. A project that listed no such difference does nothing.
- **12 November 2026, the signature check on every pull request.** Done when the project's `signatures.yml`, where it has one, runs on every pull request (no `paths:` filter) and calls the core's workflow at this sync's pin or a later one: the core's workflow now looks itself whether a package list, a lock file, an `.npmrc` or the Node version changed, and passes where none did, so the check reports on every pull request and a ruleset can require it. A workflow's change: the trusted builder's, with its two security reviews (floor rule 3).
- **12 November 2026, exact versions.** Done when the licence check passes with its new step, which this sync brings by itself where the project calls the core's `licences.yml`: every dependency a package list of the project's own asks for is the one exact version its lockfile installs, a range, a tag or an address rewritten as that version (`core/scripts/exact-versions.mjs`; floor rule 7). A project that runs the core's licence script from a workflow of its own adds `node core/scripts/exact-versions.mjs <its config>` beside it. A project whose packages are not npm's does nothing.
- **12 November 2026, the security review shown on every pull request.** Done when the project has a `security-review.yml` of its own that calls the core's at this sync's pin or a later one, as the README's "How a project takes the core", point 5, says (its triggers, and the three permissions its job grants), or, in a private repository, where its dozen or so short runs a pull request are paid minutes, when its owner has said it is not wanted; and when a security review that its reviewer's app did not post itself is posted on the PR in a comment that opens "Security review:" (`core/modules/reviews.md`, point 3), the fallback reviewer's check of a fixed security finding too, which alone settles a finding Codex marks open. The check is advisory for now: its status `security-review` always passes and says what it would have done, so nothing waits for it and no ruleset requires it yet. A workflow's change: the trusted builder's, with its two security reviews (floor rule 3).
- **13 November 2026, a security review where the change needs one.** Done when the project's own rules and docs no longer say that every PR gets a security review, nor that a sync merges without waiting where its security reviewer starts by itself (`core/modules/reviews.md`, point 3; floor rule 8); and, where a session calls the security reviewer through a plug-in, when its part says how (for Codex, `core/modules/codex.md`).
- **13 November 2026, every file a tool takes its instructions from.** Done when the project holds no such file it does not mean to have: floor rule 3 now protects them all, wherever they lie (an `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` or `REVIEW.md` in any folder, `.agents/`, `.agent/`, beside `.github/` and `.claude/`, which it already protected). `git ls-files` shows them; one nobody meant goes, in a PR of the trusted builder's, and one that stays says what `AGENTS.md` says or points to it.
- **13 November 2026, the modules a project takes.** Done when the manifest's "Modules:" line, where it is a list and not "all", names every module under `core/modules/` that fits the project: a list does not grow by itself when the core gains a module, and `copilot.md` is newer (12 November 2026) than the lists first written, so one whose project asks Copilot's review names it. A manifest's change: the trusted builder's (floor rule 3). A project whose line says "all" does nothing.
- **13 November 2026, the size marks count the same on every machine.** Done when the reading-size check passes after the sync. `core/scripts/reading-size.mjs` now counts a file without each carriage return that stands before a line feed (`core/scripts/file-size.mjs`), so a file counts the same where git converts line endings on checkout (Windows, with `core.autocrlf`) as on GitHub, and a failure on such a machine alone is no more. A repository that stores carriage returns counts lower than before: where the check says a file has shrunk, its mark comes down as the check says. A mark set on such a machine from the old count may stand higher than it need, which fails nothing.
- **13 November 2026, what a project follows.** Done when the manifest's slots hold a *follows* row (`main` or `releases`, in backticks) wherever the project wants other than what holds without one. With no row, a project whose *owner's account* is not the account the core is under follows the core's releases (`core/README.md`, "How a project takes the core", point 1): from this sync on its `core/scripts/sync.mjs` and its core-moved check take the core only from a release the core's owner cut, a full SHA aside, and say so where none is cut yet; the projects of the core's own owner follow `main` as before. Where that fits, there is nothing to do.
- **13 November 2026, the NuGet check.** Done when a project whose packages come from NuGet (.NET) has: lock files turned on (`RestorePackagesWithLockFile`, in its project files or a `Directory.Build.props`) and each `packages.lock.json` committed; a "nuget" in its licence check's config that names each of them under "ships" or "tools" (`core/scripts/nuget.mjs` says what else it takes); and a `nuget.yml` of its own that calls the core's, as `core/setup/template/workflows/nuget.yml.tmpl` has it. The check then fails, on every pull request, a package off its list: a tool that only runs whose manifest names no licence a machine can read is read by hand and recorded in the audit as `<Id>@<version>`, of "kind": "nuget"; one that ships under such a licence, and one off its list that the owner wants anyway, waits for the owner's yes and is named in "nuget.accepted" with the owner's words, and there alone (floor rule 10). A check of the project's own for its NuGet packages' licences and versions goes once this one passes with `advisory` off. A project with no NuGet packages has nothing to do.
- **13 November 2026, the NuGet check fails from the first day.** Done when a project that calls the core's `nuget.yml` no longer passes `advisory: true` to it (that stays only while a fault of the check's own is reported to the core and mended), and its audit holds no entry of "kind": "nuget" for a package that ships: each such package, its licence read by hand, waits for the owner's yes and is then named in "nuget.accepted" with the licence as it was read, the owner's words and its notice (floor rule 10; core archive 198). A project with no NuGet packages has nothing to do.
- **13 November 2026, where NuGet packages come from.** Done when a project whose packages come from NuGet (.NET) names in its licence check's config, under "nuget.sources", every source beside NuGet's own registry that a package of its lock files comes from (an https address that asks for no sign-in, or a folder of its own that holds the package files, as git lists it, ending in "/"), and nothing its build reads adds a source of its own (RestoreAdditionalProjectSources, say). The core's `nuget.yml` now gives every restore those sources and no others, which overrules a NuGet.Config, so a package from a source not named there fails the restore, and `core/scripts/nuget.mjs` reads, by NuGet's own record beside each package the restore brought, that it took none from elsewhere. A source that asks for a sign-in cannot be restored there: such a project restores in a workflow of its own and runs `core/scripts/nuget.mjs` after it. A project that takes every package from the registry, or has no NuGet packages, has nothing to do.
- **13 November 2026, the security-review check in a private repository.** Done when a private repository whose ruleset requires the status `security-review` while the check advises passes `private: true` in its call to the core's `security-review.yml`, or has turned advisory off: from this sync its job is skipped in a private repository otherwise, to bill no job for a status that only advises, and a ruleset that requires it would wait for good. A workflow's change: the trusted builder's, with its two security reviews (floor rule 3). A public repository, and a private one whose ruleset does not require the status, has nothing to do.
- **13 November 2026, the core's scripts started through bash.** Done when no workflow of the project's own runs a file under `core/scripts/` by its path alone: a game's publish of main runs `bash core/scripts/site-publish.sh root <site-dir>`. From this sync a copy of the core is the same whatever executable bit it records (a copy made on Windows records none), so a script of it run by its mode can fail with "Permission denied".
- **13 November 2026, MS-PL waits for the owner's yes.** Done when a project whose licence checks report a package or audit entry that ships under MS-PL ("REPORT:" in the licence or NuGet check's output) has an issue open for its owner, asking the yes (named then in "accepted" or "nuget.accepted", with the owner's words) or the package's replacement. Such a package that the pull request's base already shipped (in the same lock file, by the base's own config) passes and is reported; one a pull request adds, updates or moves into what ships waits for the yes, that pull request alone (floor rule 10), and so does one whose lock file a pull request moves to another path. A project with none has nothing to do.
- **13 November 2026, .NET's local tools and the fetch before the restore.** Done when the NuGet check passes on a pull request that touches the project's package files: each tool in a `dotnet-tools.json` (in `.config/` or any folder) is at one exact version and under a licence on the tools' list (what is wrong with one the base already held, no source the check reads holding it among them, is reported, not failed, while the config's sources stand as they were: a pull request that changes them has every tool read as new; one whose manifest names no licence a machine can read is recorded in the audit as `<Id>@<version>`, of "kind": "nuget"), and every package's file is fetched before the restore and held to its lock file's content hash. A project with no NuGet packages has nothing to do.
- **13 November 2026, a game's previews share its origin.** Done when a game served by GitHub Pages says in its threat model that its pull requests' previews and its live site share one browser origin (with every other Pages site of the account), so a preview's unreviewed code reads what the live game keeps in the browser, and that the game keeps nothing there that matters beyond its own saves (`core/README.md`, "How a project takes the core", point 5); where it keeps more (a sign-in, a token, anything of a player's beyond a save), that goes first. A project with no previews on GitHub Pages has nothing to do.
- **14 November 2026, the size marks' total counts the project's own files.** Done when the reading-size check passes after the sync and gives no note that the total "leaves … bytes of room above the project's own files": set the size marks' "total" to the number that note gives (the total less what the core's copy every session reads comes to, as often as the room holds it, so that the project keeps the room it had, and never less than its own files with a KB to spare). The core's own cap holds the core's copy now, so that no sync fails a project over what the core grew. A project whose check gives no such note has nothing to do.
- **14 November 2026, a listed name in a commit's author.** Done when every machine that commits in the project, the owner's own computer included, has git's `user.name` and `user.email` set (in the repository, or for the machine) to the account's login and its no-reply address (Settings, Emails), so that no commit carries a name of the project's `PERSONAL_TERMS`. The personal-terms check fails a pull request whose commits carry one, in every repository, and says how the session mends it there: that name set, and the pull request's commits rewritten with it (`git rebase --exec 'git commit --amend --no-edit --reset-author' origin/main`, then `git push --force-with-lease`), never `main`. A commit GitHub itself makes and signs (a merge, an edit on github.com) passes whatever the profile's name. A project whose commits are all made in the cloud, or that has not set `PERSONAL_TERMS`, has nothing to do.
