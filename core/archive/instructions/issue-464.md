# The reasons behind the core: issue #464

The index, and how an item is written: `archive/instructions.md`.

#464. **16 November 2026**, #464. A project is read against the core whole once, from when it takes the core, and
     after that at each release only against the rules the release added or changed, whole again after a sync that
     jumps from a copy older than the last two releases; a fresh reader that built none of it answers for each rule
     met, partly, not met or not applicable, with its evidence and what holds it there, the gaps becoming tasks at the
     dose and nothing failing, blocking or leaving the project but counts where the manifest shares them. The reader is
     a role, the auditor, which holds what every reading of what stands shares (fresh, changing nothing, evidence on a
     fixed scale, weaknesses kept out of its report, a new check only for a finding seen twice, only counts and
     conclusions leaving the project) and runs on the tool's strongest model at its default effort, its counting given
     to cheaper helpers. The core told a project what it lacked only through checks and steps, each for one rule, and
     one reading of a whole project against the whole core by hand found what no check had: rules met only in part,
     many held by review or habit; with the audit and the reading of a project's own rules there were four such
     readings, each of which would have said the same things again. The owner agreed to it as the issue sets it out,
     its points 6 and 7 later the same day. It stands behind `roles/auditor.md`, "A project is read against the core
     once, then for what each release changes" in `tasks/cleaning.md`, and `scripts/core-reading.mjs`.
