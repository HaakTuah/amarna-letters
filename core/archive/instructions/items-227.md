# The reasons behind the core: items 227 to 234

The index, and how an item is written: `archive/instructions.md`.

227. **15 November 2026** (the core; in chats with a session the owner works with, issue #313, under "What it is" and
     "The owner's word"). Asked: the session checked the floor against the two standard lists of risks, as one of nine
     such checks, and set out additions with what holds each, marked as needing the owner's yes as changes to the floor.
     Decided: the owner agreed to all of them that pass the owner's own test for a rule (#303), and so to the six points
     of #313: every named input has hostile tests (too long, the wrong type, markup, a file path, a number out of range,
     nothing at all); a failure refuses, and an error a user sees reveals nothing of the program's insides; a product
     with accounts, roles or a server takes four more rules, read only where it has them (who may do what decided on the
     side the user cannot alter and refused unless allowed, signing in through the platform or a well-known library,
     nothing cryptographic of the project's own making, a password stored only through a function made for it); a run
     with a model has a cap, in tokens or money, set by the project, and stops when it is reached; a program installed
     on a user's machine asks for no more rights than a named need, reading a saved file never runs code, and its
     installers and updates are signed and checked where the project has a certificate; and secret scanning with push
     protection is switched on in each repository. The owner's test: the criterion is rules the agents can actually
     execute on, which aid the output and make it better or more robust, not things that are only there to block. Left
     out, as the record says: rules for risks a product does not have (a single-player game in a browser needs no access
     control), agents attacking anything that is live, and a weakness written in an issue, a pull request or a file
     (floor rule 9 stands as it is). Where the mend needs the owner, a check reports and does not bind: a certificate
     for signing is the owner's to get, and switching on scanning is done by a session where its sign-in allows and
     named to the owner where it does not. To the orchestrator, passed on word for word to the builder of this rule: the
     owner's yes is given for every queued change, the floor and the review guidelines included, as its issue describes
     it, and those pull requests quote this. Behind: floor topics 5, 7, 9 and 19 and floor rule 14's cap on a run with a
     model, with the step "16 November 2026, hostile tests for every named input" in `scripts/steps.mjs`.

232. **14 and 15 November 2026** (the core; in chats with a session the owner had asked to look through the core and
     with sessions the owner works with, issue #249, its note "What this issue asks to be built, in one place" gathering
     what the owner agreed to). Asked: the owner asked for an audit of whether the core works perfectly with Kiro, to
     see whether the core can serve other projects as well. Shown the audit, the owner said the core should slot in with
     anything, ideally, that these were all areas for improvement, and asked what happens when one tool's usage runs out
     and another is used instead, or when someone uses only one tool: everything must still work. Decided: the owner
     agreed to the session's six points: one door in, `AGENTS.md`, with each tool's small entry file written from one
     list and held to it by a check; roles by what they do, not by whose tool; hooks save time and checks are the
     guarantee, no rule held by a hook alone, the hooks then carried to each tool that has the event; a short part for
     each tool, its own folders protected by name; a change of tool loses nothing, the state being in the repository;
     and a tool proven by the staged cases, tool by tool, run again at each release, the core saying of it only what its
     documentation says until it has passed. The session had proposed to keep fixed that nobody reviews their own work,
     and that the owner names who may change the protected files; the owner answered that this locks out anyone who has
     only one tool at their disposal, who can still use other sessions to review it, and saw little point in locking
     out, so both became preferences. So tools are preferences: one table of roles, the tool preferred for each and what
     takes it when that tool is not at hand, in each project's manifest with the core's default beside it, the default
     preferring Claude for the orchestrator, the sync and design; a preference orders and never refuses; the session
     that reviews a change is not the one that wrote it, a fresh session of the same tool serving; and a session the
     owner starts, of any tool, may change the protected files, guarded by what names no tool. Of why the floor asks the
     owner's yes, the owner said that rule was to prevent sessions going rogue and taking too big a mandate, not for
     when they implement what the owner asks, so they should not change the floor just to accommodate some other task.
     Agreed besides: what stands in when something outside the repository cannot be reached (issues, labels, the
     scheduled job, a review app, statuses), each named or skipped and reported, none stopping a project. Of the line
     "Nothing stops to save usage", told it said the opposite of a pace the owner had set, the owner found it a bit
     strict and said it would be more sensible to say the default is not to stop in order to save usage, with any
     preference given in the repository or in chat overruling it. And of how a builder is picked, the owner said that
     whichever provider runs the orchestrator is the foundation and the one to conserve longest, so the builder should
     be from another provider than the orchestrator; and that although one with Claude should always save it for the

     owner's (the default: no session slows or stops to save usage by its own choice; a pace said in person holds for

     work going, and the strongest model, for the work that takes judgement), and to the order a builder is picked in.

234. **15 November 2026** (the core; in chats with a session the owner works with, issue #304, whose description is its
     current text). Asked: of what the rules a session reads at its start cost on every task, the owner asked whether
     the token issue is not avoided by ensuring the agent only ever reads the ones relevant to it. Told by the session
     that the choice of what to read must be made by a machine (an entry names its modules, or a hook tells a session
     which modules its changed files call for), the owner said this is important, and asked whether it also addresses
     the earlier concern that models from not all providers can navigate the ruleset and work on the project, that is,
     whether it is agnostic to whether the tool is Claude, Kiro, Antigravity or another. Decided: the owner agreed to
     the session's five points: what is read at the start of a task is split by role, a builder reading the builder's
     part and what only another role needs moving to where that role reads it, with the cap set for each role; each
     module says in one line when it is read, in words a script can match (the paths a change touches, the labels of its
     issue, the kind of task), and an issue names the modules its task calls for; one script, given a role and a task,
     prints the files to read, and nothing else is needed to find them; any agent tool gets the same list, the script
     needing only that a tool can read a file and run a command, with a hook calling it where a tool has hooks; and it
     runs twice, at the start of a task and again before the pull request is marked ready, on the paths in fact changed,
     the session reading what that names and checking its work against it, a reviewer running the same. The owner agreed
     besides to two things being looked into, each with a short report and no rule: whether a module can be packaged as
     a skill a tool loads by itself, and whether each tool's own rule file can be written from the one source. Asking
     whether every role needs to read the others' rules, the owner suggested a folder called roles with a file for each,
     and asked whether a bug-fixer needs to read what a feature builder does. The owner agreed to the session's point:
     `roles/` holds one file for each role (the builder, the orchestrator, a reviewer, the stand-in, the design
     session); what a role reads at its start is the floor, its own file and the shared files its file names; a role's
     file holds only what that role alone needs, a rule several roles share staying in one place and pointed to; the
     file says in a line each what the role hands each neighbouring role and what it gets back, nothing of how the
     neighbour works; and the modules read by task stay apart from the roles. The owner then proposed the same split
     across the board, by mapping out every possible path each role could take and splitting everything up that way,
     folders as a principle over collections in files that must be read. The session proposed units in place of a file
     for each path, since one file a path would put the same rule in many files, and three limits: `floor/security.md`
     stays whole and is read by every session, `floor/topics.md` split by topic with its words unchanged; two things
     always read together are one file, and no unit is cut so small that opening it costs more than it saves; and the
     staged cases are run with the split reading and pass as they do with the whole reading, before the split merges.
     The owner agreed to it so. That split is built in a pull request of its own. To the orchestrator, passed on word
     for word to the builder of this rule: the owner's yes is given for every queued change, the floor and the review
     guidelines included, as its issue describes it, and those pull requests quote this. Behind: "A file for each role"
     in `modules/roles.md` and the files of `roles/`; "One script says what to read" in `modules/tools.md`, with
     `scripts/reading.mjs`, each module's opening line and the line "Read for it:" of a pull request's description; and
     a cap for each role in `scripts/size.mjs`. Behind, too, since the split was built: the folders the rules stand in
     (`roles/shared/`, `tasks/`, `tools/` and `floor/topics/`, the floor's words unchanged), the orchestrator's rules in
     `roles/orchestrator.md`, and the files that point from the paths the rules left, until the second release after it.
