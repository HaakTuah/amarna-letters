# One Node for every machine

The owner asked tonight whether anything was still duplicated between the games or departed from the core. A full
audit found each game installing Node on its cloud machines its own way. Amarna's setup fetched the official binary
with `npm pack` and checked its SHA-256. Snakes' setup ran `npm install -g node@26.12.1`, which runs that package's
install script (`preinstall`, which pulls the binary in through node-bin-setup): a break of floor rule 15 on every Snakes
cloud session, since those machines come with Node 22. The two also pinned different versions (26.13.0 and 26.12.1),
and both games' CI asked setup-node for `node-version: 26`, a range, which floor rule 7 forbids.

- **`.node-version`:** the one exact pin, 26.13.0, which projects' CI reads (`node-version-file: core/.node-version`)
  and `scripts/node.sh` installs. 26.13.0 is the newest 26.x, out on 29 October, past floor rule 7's week.
- **`scripts/node.sh`:** Amarna's checked install, moved here. It installs the pinned version where the machine's node
  is any other; runs no package's install script (`npm pack --ignore-scripts`); takes only the binary out of
  `node-linux-<arch>`, checks its SHA-256, runs it once to see its version, and only then puts it in place, through a
  temporary file beside the old one; and never installs a version with no checksum here. Its log is a fresh temporary
  file. It exits 0 whatever happens, saying what it could not do. Tested on a copy of a Node 22 binary: installed
  (checksum and version OK), present on a second run, refused for an unknown version and with no pin file, and with a
  wrong checksum left the old node in place. The checksums match the packages' binaries, which the fallback reviewer
  checked again; nodejs.org's own SHASUMS256.txt could not be read from this session (the proxy refuses it).
- **The core's own workflows** (`copies.yml`, `licences.yml`, `size.yml`) ran `node` on the runner's default, an
  unpinned Node (the fallback reviewer's P3): each now sets it up from the pin first.
- **`modules/updates.md`, "Node":** the pin and how CI and the cloud read it. **`SECURITY.md`:** Node is a tool that
  only runs, under MIT, taken as rules 7 and 15 say (the fallback reviewer's P2).

What changes in every project: its CI reads `core/.node-version`, and its cloud setup runs `core/scripts/node.sh` from
its copy on `main` in place of its own Node install, in the PR that follows this one's sync. Until the shared versions
check comes (the next PR), the pin is watched by each game's own, pointed at `core/.node-version`.

Readings taken: the pin is Amarna's 26.13.0, the newer of the two; the cloud takes the pin exactly, newer or older, as
CI does. Questions for the owner: none.
